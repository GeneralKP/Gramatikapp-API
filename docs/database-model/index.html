How to read the model

Boxes are collections; the Practice & sync view also labels browser storage and the API boundary. Arrows show logical references, with the field name and cardinality shown when you select a box. Dashed boxes are the same collection repeated from another view.

  • 1 → N means one parent can have many child records.
  • N → 1 means many records can refer to one entry.
  • MongoDB does not enforce these references as SQL foreign keys. The app joins them using ObjectIds or Anki numeric IDs.

One word, two cards

WORDS_ES_DE links a Spanish entry to a German entry. userprogresses stores each user's study cards, including the German → Spanish and Spanish → German directions.

For imported cards, itemId identifies the card and relationId identifies its vocabulary pair. Native cards also use a relation; older records can use itemId as the relation ID.

Mistakes and reinforcement

failureIndex starts with the number of Anki “Again” answers. Each wrong Check or Revisit adds 1 atomically. An attempt ID prevents a network retry from adding the same mistake twice. Undo changes the schedule without erasing mistakes.

card difficulty = max(0,
failureIndex − writingReinforcementCredit)

word difficulty = sum of its
active cards' difficulty

A completed Writing check adds up to 0.25 credit to one card for each included word, once per exercise. Lifetime mistakes remain intact. Merely generating or reopening an exercise gives no credit.

Why so many collections?

Six hold the bilingual catalog, four hold accounts and scheduling, and five hold saved Reading/Writing exercises, checks and hints.

The extra four ANKI_* collections preserve the original import, notes, cards and review log. They are an archive for verification and recovery; daily practice uses userprogresses and reviewevents.

Empty attempt collections are expected: the API creates indexes before your first submission. No new collection was added for active difficulty.

Daily new-card allowance

users.settings.dailyNewCards is an optional 0–1000 card limit shared across categories and sessions. Existing accounts fall back to their imported default deck limit (or 20). A word normally uses two places, recognition before typing. If just one place remains (including a limit of 1), recognition can use it; the first typing card waits for the next available allowance. Unused allowances do not accumulate.

Blue counts remaining eligible new cards; red counts available learning/relearning cards; green counts due reviews. A rating can move new → learning, or graduate directly to review. Setting the limit to 0 pauses new cards only.

Fast local practice

At entry, the API provides cards, counts and a serialized studyState containing scheduler options and a deterministic seed. This is a derived API value, not a stored MongoDB field. The browser uses generated copies of the server scheduling, fuzz and calendar logic.

Typing/revealing stays local. Failed Check, rating and Previous card append durable, account-scoped commands to device storage. Counters and schedules update locally; Undo retains mistakes. New directions preserve recognition-before-typing order, including when the daily allowance ends between the two directions. Sibling burial and leech suspension also run locally; Previous card restores sibling availability.

Sync and recovery

Leaving or finishing practice triggers an authenticated batch; hiding/closing makes a bounded keepalive attempt. Mobile termination can skip callbacks, so unacknowledged commands survive and retry on next launch. If the app can load while the API is unavailable, practice can use cached cards; this does not add an offline installable app or service worker. Acknowledged changes are checkpointed into cached cards and counters before commands are removed. Unusable derivative caches may be discarded and fetched again; primary commands are removed only after server acknowledgement.

The server validates IDs, ownership, original study times and schedule versions. Each acknowledged command commits independently. A flush captures the pending IDs at its boundary, so an in-flight batch cannot drain a newly started session. Existing review and failure IDs deduplicate replays. Conflicting scheduling commands stay on the device until the user chooses the server schedule; separate mistakes still sync. Choosing the server schedule also clears stale cached predictions. Saving a changed daily limit first flushes pending study, so lowering the cap does not retroactively reject those reviews.

studySyncVersion serializes concurrent new-card quota checks within MongoDB transactions. reviewevents.studySessionId and syncedAt retain session provenance; reviewedAt remains the actual practice time.

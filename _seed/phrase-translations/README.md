## Study vocabulary policy

Only verified dictionary forms enter `WORDS_DE`/`WORDS_ES` and `WORDS_ES_DE`, because these relations become study exercises. Both languages require dictionary spelling, a known grammatical category, examples, notes and a CEFR estimate. Nouns include gender and plural; verbs include past, perfect and imperative forms. Inflected adjectives, finite verbs, participles, declined or plural nouns, contractions, names and uncertain forms belong in `TRANSLATIONS_ES_DE`. The validator rejects explicit non-base morphology on dictionary entries and requires capitalization of German noun headwords.

Existing historical autogenerated `UNKNOWN` word documents and their references are retained. An entry is upgraded only when its spelling has a reviewed dictionary use; otherwise its translation is stored separately. Known categories and established metadata are preserved. Missing dictionary fields are filled, and examples/contexts are merged. German noun capitalization is significant when it distinguishes meanings such as `Verdienst` and `verdienst`.

`TRANSLATIONS_ES_DE` is shared catalog data for the Spanish/German language pair, with separate directional entries. Its compound unique key is `(sourceLanguage, targetLanguage, key)`. Surface documents hold the actual translation, lemma text, optional verified lemma IDs, morphological description, category, CEFR estimate, examples, contexts and phrase references. Lemmas not already available as verified dictionary entries are not fabricated. A final backfill links lemmas introduced later in the same seed.

## Apply and verify

These commands use the configured MongoDB connection and database `gramatikapp`. Review the JSON before applying. The seed never invokes LibreTranslate or OpenAI.

```sh
npx tsx scripts/seedPhraseTranslations.ts check
npx tsx scripts/seedPhraseTranslations.ts apply
npx tsx scripts/seedPhraseTranslations.ts repair
npx tsx scripts/seedPhraseTranslations.ts verify
```

`check` validates every reviewed record, checks that all missing tokens have a review, and compares the primary phrase fingerprint. No seed writes occur if validation fails. `apply` saves each initially pending entry in its own transaction and refreshes lemma references. Repeated runs reuse words, relations and surface keys. They skip tokens that already have a valid translation.

`repair` applies only `phrase-reference-repairs.json`: one manually checked pre-existing dangling word ID in the phrase containing `Aufenthaltserlaubnis`. It checks the exact phrase, confirms the old ID is still dangling, and requires a verified replacement word with a bilingual relation before changing the reference. It also fills absent related-word fields on manually reviewed dictionary entries with empty arrays. It does not delete vocabulary or progress records.

`verify` writes `audit-after.json`, checks every phrase token and all word/phrase/lemma references, and writes `study-entry-verification.json`. New study words and upgraded legacy UNKNOWN entries must have complete category-specific metadata and must match a reviewed source or target dictionary form. Catalog contexts are normalized dynamic study-category strings; valid legacy labels such as `prepositions` and `general_vocabulary` are preserved. `seed-result.json` records the last apply run; `reference-repair-result.json` records the repair outcome.

## Production lookup and emergency persistence

The held-word popup uses authenticated `POST /api/word-translations` with `word`, `sourceLanguage`, `targetLanguage`, and optional phrase `context`. The endpoint supports `de → es` and `es → de`. It joins all exact dictionary matches with valid bilingual relations, then checks READY surface translations. It performs no stemming.

Only an actual miss under `NODE_ENV=production` invokes the existing server-side GPT structured Responses client. One GPT call translates the word directly using its phrase context and supplies classification and complete metadata; the same validated transactional writer used by the seed saves the result. Emergency surface records have `origin: GPT` and record the model; manually seeded records retain `origin: MANUAL`. Uncertain classifications stay out of study vocabulary. A dictionary result creates or completes both dictionary entries and their bilingual relation. A surface result remains in translations. Subsequent users read the stored result without a provider request. LibreTranslate has been removed from this production flow.

An expiring five-minute lease coordinates concurrent misses across API processes. Concurrent callers receive `202 PENDING` and retry. Invalid or failed generation leaves a retryable FAILED record; the next attempt requests a fresh structured GPT result. No intermediate machine translation is stored. Invalid generation never creates a partial vocabulary pair. Browser requests have a five-minute limit and cancel on popup close, tile change or exercise change; an already-running backend save can finish.

Configure `OPENAI_API_KEY` on the production server with access to the configured GPT model (`gpt-6-luna`). No separate translation provider or key is required. Keys never reach the browser. This change does not re-run the manual seed or make external provider requests during seeding.
